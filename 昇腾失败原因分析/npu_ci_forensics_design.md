# 昇腾 CI 失败取证流水线 · 设计文档

> 配套文档：[`npu_ci_failure_design.md`](./npu_ci_failure_design.md)（第 1 步：GitHub 侧失败分析）
> 入口脚本：[`npu_ci_forensics.py`](./npu_ci_forensics.py)
> 最后更新：2026-09-24

## 1. 目标

把一次 CI 失败的定位过程固化成一条可复现的流水线，覆盖五个环节：

```
上游 workflow CI 失败 → 失败日志提取 → 借助 kubeconfig 排查现场 → 历史问题定位归因 → 根因 + 修复建议
        [第1步]            [第1步]            [第2步]                  [第4步]            [第5步]
```

其中第 1 步复用已有的 `npu_ci_failure_analysis.py`（32 桶正则 + 失败步骤时间窗 + 按 run 去重），
本工具从它的结构化产物接着往下做。第 3 步（案例选取）不是一个独立环节，而是「选哪些 job 值得花
取证成本」的裁剪策略。

一条命令即可跑通全流程：

```bash
python3 npu_ci_forensics.py                       # 跑分析 + 集群取证 + 历史归因 + 出报告
python3 npu_ci_forensics.py --handoff a.json      # 复用已有分析结果，跳过第 1 步
python3 npu_ci_forensics.py --self-check-only     # 只做集群连通性与身份自检
python3 npu_ci_forensics.py --offline             # 只用本地缓存（不联网）
```

## 2. 模块布局

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `npu_ci_forensics.py` | 驱动入口：串起 5 步、参数解析、报告落盘 | 是唯一会写文件的层 |
| `forensics/cluster_registry.py` | runner 标签 → 集群 → namespace → kubeconfig 的映射；集群身份自检 | 只返回**候选**，不做单点猜测 |
| `forensics/cluster_forensics.py` | 只读 kubectl：pod 定位、容器状态、容器日志、标签可用性核查 | 动词白名单，只读 |
| `forensics/issue_knowledge.py` | 179 个历史 issue（含 269 条评论）的知识索引与匹配 | 词面匹配 + 人工策展 |
| `forensics/knowledge_tables.py` | 32 桶的补充知识：修复动作、验证指引、关联 issue | 按桶**标签**索引，不按序号 |
| `forensics/peer_logs.py` | 多节点 job 的对端节点日志：产物匹配、节流下载、解包、**只取与切** | 不判桶（判桶仍是 `classify_text`）；不 import 第 1 步的全模块级执行脚本 |
| `forensics/report.py` | 三层证据合成、置信度阶梯、Markdown 渲染 | 冲突必须显式标出 |
| `npu_ci_watch.py` | 常驻监听器：发现失败 → 抢集群快照 → 等 job 结束后补分类与报告（见 §9） | 每个失败只处理一次；只落盘不外发 |
| `forensics/watch_state.py` | 监听台账与**纯**触发判据（什么该做、什么时候做） | 纯函数，便于单测；不落盘的守卫在写入点 |
| `deploy/` | systemd user 服务与部署/排障说明 | 部署步骤与代码同仓，避免只存在于某台机器上 |

## 3. 第 2 步：集群侧取证

### 3.1 为什么必须做这一步

多节点测试的 GitHub 日志只有 orchestrator 层，真实错误在 k8s pod 日志里（结构性缺失，日志侧修不了）。
更常见的是：**失败信号所在的层 ≠ 责任方所在的层** —— 官方分类树里的「runs-on 标签不存在 / Runner 未上线」
「pod 调度失败」这类叶子，日志里根本看不到，只能到集群侧确认。

### 3.2 集群身份：三条实测教训

集群身份错判的代价是「拿别的集群的证据解释本次失败」，比没有证据更糟，所以这三条是硬约束：

1. **runner 标签后缀不能用来判集群**。Liqo 会把虚拟节点的 pod 反射进共享 namespace，实测
   `linux-aarch64-a3-800i-*-cn12-001` 的 pod 能同时从 aiframework / cn12-001 / mind-third-ci
   三个 kubeconfig 看到。因此 `resolve_by_label()` 返回**候选集合**，由第 2 步逐个探测后用证据收敛。
2. **kubeconfig 的内部 name 字段不可信**。实测 `openmerlin-guiyang-005` 那个文件的
   `clusters[].name` 与 `current-context` 都写成 `gy-003`（复制粘贴缺陷），但 server 确实是 gy-005。
   故一律按**文件名**索引，不读 `current-context`；`name_mismatch` 只作告警，不影响判定。
3. **集群身份必须自检**。`self_check_plan()` 用「集群本地 CPU scale-set 标签」这类唯一属于该集群的
   标识做交叉验证；某个集群两个标识都拿不到时，报告明确写「无法自检」，而不是假装验证通过。

另外两条环境事实：
- `~/.kube/config` 的内容是字面量 `KUBECONFIG-DATA-FAKE`，必须显式传 `KUBECONFIG=<路径>`；
- `ascend-backend` 那个 kubeconfig 是**昇腾社区微服务集群**，不是 CI 资源集群，**不可用于 CI 取证**。

### 3.3 标签的两种形式：展示名 vs 全名

`Cluster.md`（源 = ArgoCD Application，自动生成）里同一个 machine 有两套名字：

```html
<div class="machine" data-label="linux-aarch64-a3-800t-0-cn12-001" data-npu="ascend-1980">
  <span class="machine-label">linux-aarch64-a3-800t-0</span>
```

job 在 GitHub 上报的是**展示名**（`linux-aarch64-a3-800t-0`），而 pod 名与 `data-label` 用的是
**带集群后缀的全名**（`…-cn12-001`）。不做这个映射，真实 job 会被判成「Cluster.md 未登记该标签」而
完全跳过集群取证 —— 这是一个纯属工具自己造成的假阴性。故 `parse_cluster_map()` 一次抓三元组，
`full_labels_for()` 负责翻译，查 pod 一律用翻译后的全名。

**但 `data-label` 的后缀与 pod 名实际后缀并不总是一致**（2026-09-28 实测，`ascend-cn12-001-cluster`
的同一份 `-A` 列表）：登记全名 `…-800t-0-cn12-001` 前缀匹配 **0 个**，而标签主干 `…-800t-0-`
匹配到 **6 个** —— 4 个 `…-chlqk-runner-*` + 2 个 `…-{8位hex}-listener`。也就是说后缀段实际是
`chlqk`（或 listener 的随机 hex），不是 `cn12-001`。所以「按登记全名查不到」**不能**推出
「该标签在本集群不存在」；见 §3.6 的两级匹配。

### 3.4 pod 定位：只接受「可能有本 job」的候选

`find_job_pod()` 按证据强度降序尝试，命中方式会记进 `match_kind` 并写进报告：

| 档 | 判据 | 身份是否确凿 |
|---|---|---|
| 1 | pod 名精确等于 job 上报的 `runner_name` | 确凿（后缀带 5 位随机段，不会复用） |
| 2 | `runner_name` + `-workflow` 伴生 pod | 确凿 |
| 3 | 以 `runner_name` 为前缀（后缀段可能被截断） | 确凿 |
| 4 | 按 pod 名文法拆出 runner 标签，与 job 标签求交 | **推定**（靠标签猜的） |

第 4 档证据标准是「有正面佐证」而非「没被排除」，要连过三关：

1. **真的启动过**：`phase=Pending`（还没调度上）或没有任何 `containerStatuses`（容器从未创建）→ 剔除。
   从未启动的 pod 不可能承载一个已结束的 job，与时间无关。
2. **存在起点早于失败步骤**：承载该步骤的必要条件是 pod 先于该步骤存在。起点取
   `status.startTime`，缺失时退到 `metadata.creationTimestamp`（Pending pod 没有 startTime，
   而 creationTimestamp 由 API server 写入，永远存在）。
3. **起点判不出来也不收**：缺两种时间戳时是「不知道」，不等于「可以采信」。

第 1、2 关都是实测踩出来的：

- **踩坑 A（复用 pod）**：runner pod 会被复用，同一 scale-set 的 pod 连续接多个 job。实测某 job 的失败
  步骤在 `09:37:19~09:37:21`，而按标签+时间窗「收敛」到的 pod 启动于 `09:38:53`，日志里正在续租的是
  **另一个** job。曾用「pod 启动不晚于 job 结束」+120s 余量做判据 —— 方向就是错的：job 结束后新建的
  pod 照样满足它，判别力为零，92s 的间隔就是这么溜过去的。正确方向是「早于失败步骤开始」，余量压到 60s。
- **踩坑 B（未调度的 pod）**：实测两例 12 分钟前失败的 job 匹配上了**刚刚才创建**的 Pending pod，
  其 `PodScheduled=False Unschedulable`（PVC 未绑定）读起来还挺像失败原因。只看 `startTime` 会让
  「时间未知」被当成「可能就是它」。独立复核证实：该标签下现存 pod 最早创建于 `09:45:52`，
  而目标 job 的失败步骤在 `09:36:02` —— 现存 pod 确实全都不是本 job 现场。

第 1、2 档不做这种剔除：pod 名精确一致时身份是确凿的，时间戳对不上只说明**时间戳本身**可疑，
不足以否定身份。此时降级为「⚠️ 时间戳存疑」提示并仍按精确匹配采信，不能反过来把最硬的证据丢掉。

**报告措辞**分开三种否定结论，它们的含义完全不同：

- 找到的不是本 job 的（`同标签有 N 个候选 pod，但全部不构成本 job 的现场证据（X 个起点晚于…、Y 个尚未启动的）`）
  → 集群里该 runner 确实在滚动，只是本次现场已被回收；
- 没法判定的（`均无法判定是否承载过本 job（缺可信的时间判据），未取证`）；
- 压根没找到的（`pod 已回收（历史失败的常态）或未在本集群找到`）。

### 3.5 取到的证据与权限天花板

能取到：pod phase / node / QoS / 创建与启动时间、容器状态（`state`/`lastState.terminated`
的 reason 与 exitCode）、重启次数、init 容器失败、非 True 的 condition、容器日志（含**重启前实例**的日志，
`previous=True`）、标签可用性核查。

取不到（SA 权限所致，报告里作为已知局限写明）：`nodes`/`events`/`namespaces` 全 Forbidden，
故**没有调度事件**（`FailedScheduling` 的具体原因）、没有节点 condition 与 taint，
`kubectl describe` 的 Events 段会 403。

`lastState.terminated.reason` 是集群侧最有价值的一格：它能区分三件在日志里长得一样的事 ——
`OOMKilled`（内存）/ `137 + Error`（可能被 drain 杀）/ `Completed`（正常退出但 job 判失败）。

### 3.6 降级路径

pod 已回收是历史失败的常态。此时不做假装取证，而是降级为**标签可用性核查**：逐个候选集群查
该标签下现存的 runner / listener 数量。这是**查询时刻的快照**，查到「无 runner」只能说明此刻没部署，
**不能**证明失败当时 runner 掉线，因此它不计入 owner 票，只作提示并强制人工确认。

可用性核查**分两级**（§3.3 的实测就是这个原因）：

| 级 | 前缀 | 证据强度 | 命中后停止 |
|---|---|---|---|
| 1 | 登记全名 + `-`（`…-800t-0-cn12-001-`） | 强 | 命中即返回，命中数与旧口径**逐字段一致** |
| 2 | 展示名 + `-`（`…-800t-0-`），要求名字含 `runner`/`listener` 标记 | 弱 | 仅在①0 命中时进行 |

第 2 级是兜底，代价是前缀变宽必然引入污染，故：①要求 runner/listener 标记（挡住同前缀的
agent/daemon 之类工作负载）；②保留结尾 `-`（挡住 `…-800t-03` 这个**另一个** runner 池）；
③把实测到的后缀变体（`{chlqk: 4, 848db74b: 1}`）与登记后缀一并列出，让读者看到的是
「登记后缀与实际命名对不上」这个**具体事实**，而不是一个布尔值。

结论措辞据此分三种，互不替代：

- **全名命中** → 「标签有效，失败不是标签不存在导致的」；
- **仅主干命中** → 「标签族确实在线（N 个 runner / M 个 listener），但对不上的是**登记后缀与实际命名**
  （注册表问题），**不是** runner 未上线」——并转人工修正 Cluster.md 登记；
- **两级都 0 命中** → 阴性结论，必须写明查过哪些匹配方式（`scopes_checked`），
  否则读者会以为只按登记全名试过一次 —— 而那正是假阴性的来源。

前两种都**不**计入 owner 票（同「查询时刻快照」的理由）；第三种同样不计入，只作提示。

## 4. 第 3 步：案例选取

优先级：① 日志侧明确要求集群取证（`cluster_todo`）→ ② 桶知识表标了 `probe`（该桶结论需集群侧验证）
→ ③ 其余。跳过假失败。

同一优先级内**按桶轮流取**（round-robin），而不是直接取前 N 个：实测 `--max-cases 4` 取到的
4 个 job 全是同一个桶（都是「Wait for pods ready」），报告看起来做了 4 份取证，实际只有 1 份信息。

### 4.1 日志侧已定性的 case：提前退出，且不占名额（2026-09-28 新增）

第 1 步在日志里看到**测试框架自己打印的判定行**（pytest 的收集结果/退出码）且结论指向业务侧时，
会把该条分类标成 `decisive`。下游据此**提前退出**第 2 步：

- `select_cases()`：`decisive` 的 case **必进报告，但不占 `--max-cases` 名额**，并排在最前（先读先办）。
  名额是留给「不查集群就定不了性」的 case 的 —— 被已定性的占掉，等于少查一个真需要查的，
  把提前退出省下来的预算又浪费回去。
- 主循环：`cluster_result = step3_skip_cluster(item)`，**一次集群调用都不发**（连快照也不查）。
- 报告：写「取证集群：**按规则跳过**」，措辞与「未取证」严格区分 —— 后者是「查了没查到」，
  语义正好相反；`跳过` 的 case 也不计入「集群侧取得 pod 实证 N/M」的分母（否则取证成绩看起来变差）。
- `knowledge_tables`：这两个桶的 `probe` 为 `None`（集群侧给不出新信息），修复建议第一句就写明
  「无需集群侧取证」，并给出判定依据与修法（rebase 到含改动的提交 / 保证脚本与代码同源）。

⚠️ **不能把这类 case 从列表里直接剔掉**：报告只渲染传进去的 `cases`，归因分布也由 `cases` 统计，
剔掉等于让业务侧失败从此在报告里消失（静默丢信息），而不是「少花一次集群查询」。

对应的分类侧规则（`DECISIVE_BUCKETS` 与 `is_decisive()` 的两条判据、为何必须排在硬件桶之后
又排在通用包装桶之前）见 [npu_ci_failure_design.md](npu_ci_failure_design.md) §7.2 与 §7.4。

⚠️ **监听器阶段 A 为同一 job 抢下的快照，对已定性的 case 也不消费**（连 `snapshots/` 都不读）：
判据来自测试框架自身、不需要旁证，而把两层证据混进同一个结论会让一条本已清楚的业务侧判定
重新变成「需人工裁定的冲突」。快照文件仍留在 `~/.forensics_state/snapshots/`，可随时人工查阅。
**已知残余风险**：若容器是在 pytest 给出 `ret=1` **之后**才被 OOM 杀死，日志侧看不到该信号，
本规则会直接判业务侧 —— 这种情况请人工核对同一个 job 的快照文件（`lastState.terminated.reason`），
那正是「快照不消费」这一取舍的代价，写在这里以免被当成「已排除」。

## 5. 第 4 步：历史归因

知识库 = `ascend-gha-runners/docs` 的 issue（含评论；根因常在评论里，故 `root_cause_source` 会标明
取自正文还是评论）。

### 5.1 匹配：签名 + 关键词，IDF 加权

- 签名（`extract_signatures()` 统一产出，如 `errorcode:507035`、`exitcode:137`）权重 3.0 × IDF；
- 关键词（含 CJK 2-字滑窗 bigram）权重 0.4 × IDF；
- 签名与关键词都做归一化，避免同一现象的多种写法互相错过。

### 5.2 三个反「看起来很有道理」的校准

1. **出处 ≠ 机制**。实测 `schedule_nightly_test_a2` 只出现 1 次（按 IDF 是「稀有词」），但它只是
   **工作流名**：命中它只说明「同一个 workflow 里的另一次失败」，不代表同现象。故 workflow / job /
   step 名统一作为 `provenance` 传给匹配器排除。
2. **异常类名不是机制证据**。`valueerror` 在本库 `df=3`，按 IDF 算「稀有」，可它只是 Python 异常
   **类名**。实测 #190/#254/#101 都靠它被标成「证据强度=强」，而它们与缓存未命中毫无关系。
   故 `GENERIC_SIGNATURES` 把异常类名（以及 `ERR99999` —— 本工具知识表已明确它是昇腾对任意未捕获
   应用层异常的通用包装，不是硬件信号）排除在机制证据之外。
3. **中文切词**：STOPWORDS 收进了 2 字虚词（我们/这个/可以/没法/…），否则滑窗产生的虚词 bigram
   会稀释 IDF，让真正的症状词失去区分度。

### 5.3 先例机制

`match()` 除了取 top_k，还**保证给复盘留槽位**（`precedent_k`）：实测 top_k=5 时 5 个名额全被
非复盘 issue 占满，导致「先例」机制静默失效 —— 命中了却永远没先例。

先例不是「高分」就算，而要看证据类型：

| 证据强度 | 含义 | 报告措辞 |
|---|---|---|
| 强 | 命中带机制的签名（如 `exitcode:137`） | 「与历史先例 #N 高度吻合」 |
| 中 | 只命中核心症状词（稀有且非出处名） | 「与历史先例 #N 主题相近（可参考，但机制未必相同）」 |
| 弱 | 只命中通用词/出处名 | 不采信为先例，列为「分数不低的线索」提示人工核对 |

### 5.4 策展关联：词面匹配连不上的同一现象

本工具说「模型缓存未命中」，历史 #238 说「找不到缓存模型」，两者无稀有词重叠（#238 只得 11 分、
排 44 名）。这类**已知同现象**靠 `knowledge_tables.py` 里按桶登记的人工策展 `related_issues` 兜住，
每条都写明「为何关联」。策展表是有限的、需要人维护，报告里凡出自策展的条目都会标明，不冒充自动发现。
（这条也是本工具最大的固有局限，已写进报告的「已知局限」。）

## 6. 第 5 步：合成与输出

### 6.1 三层证据并列

日志侧（桶 + owner）、集群侧（pod 实证 / 标签可用性）、历史侧（先例 + 策展）三层各自陈述，
**冲突显式标出**而不是取其一：

- 集群侧实证与日志侧 owner 不一致 → 记冲突；
- 日志侧判 `code`，而先例/策展的根因提到平台侧动作 → 记冲突并提示「错误信号所在层 ≠ 责任方所在层」，
  但**不自动改判**；
- 集群侧「查无 runner」这类快照级负向结论 + 历史先例 → 记「需人工确认」的提示项，不记冲突。

**日志侧内部的第二证据源：对端节点（2026-09-29 新增）**。多节点 job 的 job log 只有 node0 一台机器，
node1..nodeN 只在 `*-ascend-logs` 产物里（取值链路与实测规则见
[`npu_ci_failure_design.md` §7.5](./npu_ci_failure_design.md)）。报告里的位置与措辞：

- 位置：`render_case()` 的**「对端节点日志（第 1 步第二证据源）」**一节，紧跟失败步骤时间窗、在
  「集群侧现场」之前 —— 它与 node0 的日志同属一层（容器 stdout），不该与集群证据混排；
- 内容：产物名 + artifact_id（标明本次下载还是本地缓存）、各对端节点的行数与取尾行数、命中桶、
  首条异常原文（`<details>` 折叠）、以及重新取回全文的 `gh api` 命令；
- **每一档都要出话**：有文本 / 产物存在但为空 / 未取得 / 只有 node0，四档各有措辞。
  留白会被读成「对端节点无异常」，而实测「产物存在但为空」恰恰意味着该 job 在容器日志产出前就已失败
  （run `36518916532` 的 9 个失败多节点 job 里 8 个如此）；
- 采用策略**仅兜底**：node0 判出桶就沿用（对端只作并列证据，依据行注明「未参与本 case 定性」）；
  只有 node0 判「未分类」时才采用对端桶，此时依据**首行**改写为
  「日志侧：node0 失败步骤时间窗**未能分类**，采用对端节点日志判桶 → 【…】」——
  不这么写，读者会以为 node0 的时间窗本身命中了这个桶，而两者的证据强度差一个档。

### 6.2 置信度阶梯

| 条件 | 置信度 |
|---|---|
| 三层证据冲突 | 低（需人工裁定） |
| 集群侧实证 + 与日志侧一致 | 高 |
| 命中同签名先例（强），缺集群侧实证 | 中高 |
| 有同主题先例（中，机制未必相同） | 中 + 需人工 |
| 集群侧已定位 pod 但状态无异常 | 中 + 需人工 |
| 仅日志侧正则定性 | 中 + 需人工 |
| 未分类 | 低 |

**只治理了否定结论、没有任何正向证据，不能提升置信度**。有「需人工确认」提示项时，`needs_human`
强制为真。

**靠对端节点兜底定性的 case 不给「高」**（2026-09-29 新增）：那个桶是从产物的**尾部粗切**文本里判出来的，
与失败步骤没有时间窗对齐，而 node0 自己什么都没判出来。集群侧即便一致，也只是「同一台机器的旁证」，
不等于给这段粗切文本补上了时间基准。故这类 case 置信度上限为「中（采用对端节点日志兜底定性，
对端文本无时间窗对齐）」，并追加一条需人工确认的提示项（按该节点的时间戳复核后再落库）。
判据是**来源**（`sig_source == "对端节点日志"`）而不是桶名 —— 同一个桶若由 node0 的时间窗判出，照常可给「高」。

### 6.3 输出

- Markdown 报告（人读）：逐案列根因 / owner / 置信度 / 依据 / 冲突 / 修复建议 / 先例；
  另附集群取证可用性表、集群现场快照、已知局限、执行期间的错误。
- 结构化 JSON（机读）：与报告同源，便于后续接看板或回归比对。
- 权限受限、拿不到的东西一律写「未取证」，不用推测填充。

## 7. 已知局限（摘录，完整清单随报告输出）

- **官方分类树不含正文**：`problem-tree.json` 的 19 个叶子节点 text 为空，只能对齐分类口径，
  不能提供根因描述 —— 建议内容来自桶知识表 + 历史 issue 先例。
- **靠标签定位的 pod 是「推定」而非「确证」**：参见 §3.4。同一窗口内该 scale-set 若并发跑过多个
  job，仍需用容器日志里的 job 号二次确认。
- **标签可用性核查是快照**：见 §3.6。其中「登记后缀与实际命名不一致」是**注册表**问题（实测
  `cn12-001` vs `chlqk`），工具只能靠标签主干兜底并如实标注，修不了 Cluster.md 本身。
- **换说法的同一现象，词面匹配连不上**：见 §5.4。
- **分数高 ≠ 同现象**：实测 #228（AOP bisect 超时）仅凭 `schedule_nightly_test_a2` 这个工作流名
  就拿到 65 分。故对每条匹配都标证据强度，且只让「强/中」充当先例。
- **不自动裁定责任方**：历史先例只作线索，冲突交人工。
- **多节点 job 的 job log 只覆盖 node0 一台机器**：其余节点的日志只在 `*-ascend-logs` 产物里，
  而该产物**可能为空或未上传**（实测一次真实 run 的 9 个失败多节点 job 里 8 个为空，
  它们多在容器日志产出前就已失败）。且产物里的文本是整段容器 stdout，**没有失败步骤的时间窗对齐**，
  只能取尾部若干行。故对端证据仅作兜底、不作覆盖，且这类 case 不给「高」置信度（见 §6.1/§6.2）。

## 8. 交付面与验证方式

- 第 1 步的交接面是 `--emit-json` 产物（`failed_jobs` / `classifications` / `cluster_todo`），
  `--handoff` 复用它，因此本工具可以在不重跑 GitHub 分析的情况下被反复验证。
- 缓存：`.forensics_cache/{Cluster.md, issues.json, comments.json, analysis_handoff.json}`
  （Cluster.md 默认 24h 过期；取不到网络时宁可用陈旧缓存，也不让集群归属环节整体失效）。
- 回归样例：`/tmp/test_handoff.json`（3 个合成案例）用于端到端冒烟，覆盖「有先例无实证」
  「同签名先例」「三层冲突 + 策展关联」三种梯度。
- 实测（2026-09-24，近 7 天、a2+a3）：70 个失败 job → 40 条分类 → 8 条待集群取证 → 8 个案例，
  集群侧 0 个 pod 实证（现场均已回收，逐个给出了否定理由）、2 个案例存在证据冲突。
- 测试：`tests/` 下 9 个独立可运行的套件（无需 pytest），共 104 条断言。每个套件都做过
  **证伪验证**：把被守住的缺陷重新注入，确认它会红（而不是只看它现在是绿的）。
  `tests/test_pytest_verdict.py` 另含一条**端到端**断言（真跑 `npu_ci_forensics.main()`，
  用 spy 包住 `step3_cluster_forensics` 记录「谁去查了集群」）：提前退出的定义就是这份名单里
  没有已定性的 job —— 零件测试测不出接线错误（三元表达式写反、`select_cases` 漏传），这条能。
  `tests/test_peer_logs.py` 覆盖对端节点日志与拆桶：产物名从 job 名推导（含 GitHub 中间截断）、
  同构构造的产物解包（含「产物存在但为空」形态）、兜底采用策略、以及两处**反例**
  （空产物不得写成「对端节点无异常」；对端文本里的 `ret=1` 不得让 case 变 `decisive`）。
  产物 fixture 为按实测形态**同构构造**（不提交真实产物字节：43KB 的 zip 里是真实 CI 容器日志，
  含内网地址与节点名，不宜入库）。
- 监听器实机验证（2026-09-28）：真实失败 3 例全部流转到 `reported`；对**仍在运行**的 job
  抢到快照（`runner_name` 精确匹配、12809 字节真实容器日志），报告出现
  「证据来源：失败时刻的集群快照」并带退出码注意事项；复跑同一 handoff 耗时 0s（未做实时查询）。
  同日常驻期间累计 `reported=4`。
- 监听范围实测（2026-09-28，逐条查 API）：加事件过滤前后「落在范围内」由 8 个降到 7 个，
  被剔掉的正是那只 2026-05-15 的僵尸 run（`event=pull_request`）；余下 7 个的 `event`
  **全是 `workflow_dispatch`**，见 §9.3。

## 9. 监听器：把第 2 步的时间窗抢回来

### 9.1 为什么必须常驻、且必须两阶段（全部为实测数字）

流水线本身没问题，问题是它得**人工记得跑**，而最值钱的第 2 步只在很短的窗口内有效：

| 实测项 | 结果 |
|---|---|
| 「失败步骤结束 → job 结束」 | **55s / 56s / 55s**（3 例，稳定） |
| 进行中的 job 能否读到失败步骤 | 能（`steps[]` 与 `runner_name`/`labels` 都已填充） |
| 进行中的 job 能否取日志 | **不能**，HTTP 404 `BlobNotFound`（日志 blob 尚未生成） |
| runner pod 存活期 | job 结束前后即被回收；实测失败 9 分钟后同标签 pod 已换人 |
| 集群快照全程（冷启动、单候选、未命中） | 4.75s（`-A` 列举 3.77s、namespace 级 0.89s、容器日志 0.53s/容器） |

于是「能取日志的时刻」与「pod 还活着的时刻」**几乎不重叠**：

```
【阶段 A】看到某个步骤失败（此刻 pod 必在）→ 立刻抢集群快照
【阶段 B】等 job 结束（此刻日志才可下载）  → 补日志分类 + 历史归因 + 报告
```

合并成「等结束后一起做」→ 永远拿不到 pod；合并成「失败时就做」→ 永远拿不到日志。
这不是保守，是接口事实，所以监听器结构上就是两阶段的。

### 9.2 台账：绝不重复分析，也绝不静默丢弃

台账键是 **job_id** 而不是 run_id：同一 run 里可能有多个 job 先后失败（实测相隔数十分钟），
按 run 记会把后失败的那个吞掉。状态机：

```
seen ──► snapshot_ok / snapshot_missed ──► analyzed ──► reported
seen ──► not_a_failure（job 结束后确认并非失败，如 continue-on-error 的步骤）
任一路径 ──(出错累积到 --max-attempts)──► gave_up（保留 attempts 与 last_error）
```

两类错误各自对应的真实风险：**重复分析**会把日志 API 调用量放大几十倍（日志下载是整条链最贵的一步）；
**静默丢弃**则让报告里既没有该失败、台账里也没有痕迹，看起来像「这个失败不存在」——
故失败一律记 attempts，最终置 `gave_up` 留痕。

`should_take_snapshot()` 只在「job 未结束」或「结束 ≤ 90s」时抢快照；更早的 job 记
`snapshot_missed` 并写明「pod 早已回收，此时再查只能查到同标签的**别的** pod，属假证据」——
不把「没抢到」伪装成「已取证」。

### 9.3 四个把时间花在刀刃上的取舍

- **自适应轮询**：有目标 run 在跑时 `--interval 30`，空闲时 `--idle-interval 300`。
  目标 workflow 一天里大部分时间没在跑，一直 30s 轮询等于一天约 2880 次空转调用。
- **Cluster.md 与 kubeconfig 索引常驻内存**，按 `--max-age-hours`（默认 24h）刷新，不每轮重抓。
- **范围按「路径 + 触发事件」双重限定**：path 正则收 nightly/weekly 的 a2·a3（用 path 而非 name，
  因为 path 是 `failed_jobs[].workflow` 的口径，两边能对上）；事件只收 `schedule` +
  `workflow_dispatch`。这条口径**两个方向都踩过坑**，故写成断言：

  | 实测（2026-09-28，逐条查 API） | 结论 |
  |---|---|
  | 范围内 7 个真 run 的 `event` | **全是 `workflow_dispatch`** |
  | 三个 workflow 文件的 `on:` 块 | 只声明了 `workflow_dispatch`（nightly 由上游调度 workflow 拉起） |
  | 那只 2026-05-15 的僵尸 run | `event=pull_request`，`head_branch=bugfix/version-suffix-9167` |

  收少了（字面「仅 schedule」）→ 7 个全被排除，**且不报错**，表现为「上游一直没失败」；
  收多了（不筛事件）→ 把「改 workflow 本身的验证」也当 nightly 失败来抢快照。
  `event` 字段缺失时按**在范围内**处理：漏看一次真失败的代价高于多查一次 `/jobs`。
- **从未开始的 run 超过 24h 判为僵尸**：僵尸让 `active` 恒为真 → 服务永不休眠。实测代价为
  夜间空闲时段从约 46 次/小时被抬到约 419 次/小时，多出来的全是给一只永远不会有 job 开始的
  run 查 `/jobs`（GitHub 不会把它标成失败，`updated_at` 也停在创建那一刻 —— 除年龄外没有别的
  信号）。判据刻意限定在「未开始」（`queued`/`requested`/`waiting`/`pending`）：真在跑的 run
  无论多老都要盯着，它的 job 随时可能失败。每个 run_id 只在日志里记一次，游标随台账落盘，
  进程重启不会把同一只僵尸再报一遍。

### 9.4 演练暴露并已修的三个缺陷（都不是「新功能」而是既有实现错了）

1. **`mark()` 无限自递归** —— 一次机械替换把 `Ledger.note(...)` 换成了 `self.mark(...)`，
   连 `mark()` 自己的函数体也被换掉。`--dry-run` 一直是绿的，因为 dry-run 在那行之前就返回了。
   修法：恢复写入调用，并把「不落盘」从各调用点收进 `Ledger.save()`（`read_only`），
   使 dry-run 只有真实路径才可能暴露写入口的错。
2. **namespace 假阴性** —— Cluster.md 把仓库登记到项目共享 namespace（`vllm-project`），
   而 runner pod 实际在仓库名派生的 `vllm-project-vllm-ascend`；旧实现把「namespace 能列举」
   当成「namespace 正确」，报告于是写成「pod 多已回收」——而那个 pod 当时已运行 9 分钟。
   修法：登记 namespace → 派生 namespace → `-A` 全量，逐个尝试、命中即停（见
   `tests/test_namespace_lookup.py`）。
3. **标签后缀不匹配导致可用性核查假阴性** —— 见 §3.3 / §3.6 的实测（0 个 vs 6 个）。

前两个是「工具自己造的假阴性」，后一个是「工具信了登记信息而登记信息是错的」。
共同点是：**都不会报错、不会崩溃，只会安静地把结论说反**，因此三者都由断言守住，
并各自做过证伪验证。

### 9.6 第四类：步骤名判错 → 归因与取证方向都反了（2026-09-28 修）

`Stream logs` 被当成「日志回传步骤」（看着像收尾），于是归因路径判成 `no_log`：
**不读日志、直接判 infra**，再让第 2 步去集群找 runner pod 是否被驱逐。实测它是多节点 job
里**跑测试的那一步**，日志里就写着责任方：

| 真实日志形态 | 实际根因 | 旧口径结论 |
|---|---|---|
| `ERROR: file or directory not found: …` + `collected 0 items` + `pytest exit code: ret=4` | 测试脚本与被测代码**版本错配**（入口文件不在被测分支里），业务侧 | infra「Runner 与 GitHub 通信问题」 |
| `FAILED …::test_external_dp` + `1 failed in 3631.38s` + `pytest exit code: ret=1` | 用例真失败，业务侧 | 同上 |

两层包装（`Some tests failed` → `Executing the custom container implementation failed`）
把「一条用例都没跑」说成「测试失败」，很容易被判成产品缺陷；而该桶占历史语料 **19%（第二大桶）**，
即这类误判的规模不小。修法（三处联动）见 §4.1 与本仓
[npu_ci_failure_design.md](npu_ci_failure_design.md) §7.2/§7.4：
`Stream logs` 改走 `window_tail` 读日志 → pytest 判定行单独成桶（排在硬件桶之后、通用包装桶之前）
→ 命中即 `decisive`，第 2 步提前退出并在报告里写明「按规则跳过」。

教训（与前三类同构、但入口不同）：**步骤名像「收尾」不等于它是收尾**。
判定依据只能是它实际执行了什么；「名字看着合理」正是这类错判能长期存活的原因。

### 9.7 部署

见 [deploy/README.md](deploy/README.md)：systemd **user** 服务（凭据都在用户目录，
不复制到 root）、`loginctl enable-linger`（否则登出即停）、以及一条实测过的坑 ——
`ExecStart` 所在服务的 PATH **不含** `~/.local/bin`，而 `kubectl` 正装在那里；
少了它每次集群取证都会变成「未找到 kubectl 可执行文件」，台账里全是
`snapshot_missed`，而写的理由（pod 已回收）还是错的。
